# Decisions

| # | Decision | Why | Status |
|---|---|---|---|
| D1 | Journeys are trees: one incoming connection per step, no merge paths. Language paths duplicate the steps after the split. | Keeps insert-on-connection, delete, collapse, validation and layout simple; merge paths are out of scope. | Settled |
| D2 | Edges carry the path key (`label`): the segment id, `Remaining`, `Opened` / `Clicked`, or the shuffle path name. The canvas shows the display label. | Renaming a segment or changing a percentage must not break the connection. | Settled |
| D3 | Deleting a split keeps its first path (spliced into the previous step) and drops the other paths; deleting a single-outlet step splices it out; deleting a terminal leaves the connection open. | Least surprising on a tree; the open connection is flagged by validation. | Settled |
| D4 | `canEdit` is the single rule for Active / Closing: only `contentId` of a Delivery. The change is logged as "Content changed by X at T". | The brief; the version bar, panels and View changes all read the same rule. | Settled |
| D5 | The Delivery stepper is Channel → Content → Details, titled "Create" on its first screen, which also holds the delivery name. | The brief lists those three contents; the name needs a home. | Open |
| D6 | "Skipped" as a contact status = the contact reached Exit after its last Delivery was skipped. Inside the journey a skipped contact continues. | The brief's status list; skipping is per step. | Settled |
| D7 | Payment failed v3 = v2 + one Push step on the FR path + the FR wait changed 2 → 1 days. | The brief: one step added, one wait changed. | Settled |
| D8 | Sends are attributed to the Delivery's offer: an Offers table in Monitor › Overview and "attributed to CODE" in the contact timeline. No offer page. | The brief; offer pages are out of scope. | Settled |
| D9 | Every number in Monitor comes from `CONTACT_STATES`, written by a seeded walk of a few hundred contacts per journey. | "Do not hard-code stats"; counts add up across splits by construction. | Settled |
| D10 | Steps can be dragged freely in a Draft; the position is saved per step and per orientation, and the *Auto-layout* button puts every step back. Locked versions and the Monitor keep the automatic layout. | Asked for by the owner after review; the brief's "auto-layout only" stays the default. | Settled |
| D11 | A Draft's step cards carry a × to delete (as in CM-New-UI-UX2); on a locked version, selecting a step shows once why it cannot be edited. | Review feedback: deletion was not discoverable; the lock was silent. | Settled |
| D12 | "+ New journey" opens the editor directly with defaults; event, entry mode and contact list are edited in the Event entry panel. The contact list is one of the existing datamarts (`DATAMARTS`), not a Customers / Prospects switch. | Owner's review: one click less, and lists already exist in the Datamart catalogue. | Settled |
| D13 | Node cards carry inline controls (foreignObject in the SVG card) for the key settings; card and panel call the same `commitStepField`. Locked versions show plain text except Delivery → Content. | Spec update after review (Symplify / old ECM builder parity). | Settled |
| D14 | The Event entry's "entry segment" is an optional filter (Any contact by default); contacts outside it are ignored at entry. It is not a segment-based entry. | The spec update lists it as an inline field; the product rule "no segment entry" still holds. | Open |
| D15 | One Wait step with the type inside (Duration / Until / For event / For segment match). Changing the type renames the first connection to the new first path and drops the others. Two-path waits log a `split` event like the other splits, so the Monitor shows counts and % on their paths. | Spec update. | Settled |
| D16 | A branch is removed by deleting the first step after it from its card × or the panel (a Parallel split path also from the path's ×); the steps after it go too, since a journey is a tree and nothing can float; the path stays open and validation flags it. Connectors carry no × (superseded by D20). | Review feedback: branches must be removable; the connector rework removed every default-visible control on the canvas. | Settled |
| D17 | ~~Parallel branches from a single-outlet step (`∥n` edges).~~ Superseded by the Parallel split (D21). | Review feedback: two steps after an Event must be possible. | Superseded |
| D18 | Free positions are cosmetic: any structural change puts the canvas back on the automatic layout. The + on a connection inserts in sequence; a second branch needs a split (Parallel split for "all at once"). | A dragged card next to a newly inserted one produced crossing connectors. | Settled |
| D19 | ~~Port-to-card drag connects steps.~~ Withdrawn by the connector rework (D20): the orange ports and the card + are gone; a parallel branch is added from the panel and filled through its ghost card. | Spec update: nothing visible on connectors or cards by default. | Superseded |
| D21 | Parallel split replaces the `∥` parallel branches: 2–5 paths "Path n", contact tracked per path (`legs`, log entries tagged with the leg), status Exited only when every leg exited; a contact's "current step" is the first leg still inside. No merge: each path ends in its own Exit. | Spec update: branching only through splits; per-path ContactState. | Settled |
| D20 | Connectors are orthogonal (elbow) paths like Symplify: a short trunk, a spine, one branch per path with a label pill at its start using the card's path letters. Fixed column / row spacing so a single next step gets a straight line. Open paths end in a ghost "+ Add step" card; validation never colours a connector. The hover "+" on a connector is the only control on it. | Spec update (canvas rework). | Settled |
